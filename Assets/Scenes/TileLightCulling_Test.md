# 타일 광원 컬링 테스트 씬

`TileLightCulling_Test.scene`을 에디터의 씬 열기로 불러온다. 현재 JSON 로더가 요구하는 이름, GUID, 루트 컴포넌트와 계층 목록을 포함한 형식이다. 내장 CubeMesh만 사용하므로 별도 메쉬나 텍스처를 가져올 필요가 없다.

## 배치

- 바닥, 뒷벽, 깊이가 다른 큐브를 포함한 메쉬 13개.
- 벽 앞에 분산된 색상별 Point Light 12개.
- 타일 경계를 가로질러 움직여 볼 청록색 Point Light 1개: `Test_BoundaryPoint_MoveThis`.
- +X 방향으로 벽을 비추는 노란색·자홍색 Spot Light 2개.
- 화면 밖 Y ±140~170 위치에 있는 Point Light 32개.
- 비교 중 물체 형태가 보이도록 약한 Ambient Light 1개.

Point/Spot 합계는 47개로, 현재 타일 목록 용량 200개보다 작다. 이 씬은 용량 초과 검증용이 아니다.

카메라는 (-14, 0, 7)에서 회전 (0, 0, 0), FOV 60도, Near 0.1, Far 80으로 시작한다. 화면 정면의 벽에 지역별 조명 변화가 나타나도록 배치했다. 실제 화면은 엔진에서 실행해 확인해야 한다.

## 비교 순서

1. `Lit_Lambert` 또는 `Lit_Phong`에서 테스트한다. 현재 Gouraud는 전체 광원 루프를 사용하므로 컬링 비교 대상에서 제외한다.
2. 같은 카메라와 같은 뷰포트 크기에서 전체 광원을 순회하는 기준 경로와 타일 목록을 읽는 경로를 비교한다. 씬 파일 자체는 렌더러의 경로를 전환하지 않는다.
3. 정상적인 컬링이라면 두 경로의 조명 결과는 같아야 한다. 색 영역이 사라지거나 타일 모양의 밝기 경계가 생기면 광원 누락 또는 타일 번호 불일치를 의심한다.
4. `Test_BoundaryPoint_MoveThis`의 Y 위치를 -8에서 +8 사이로 천천히 이동한다. 밝기 변화가 연속적인지 확인한다. 광원 범위를 바꿔 여러 타일을 덮는 경우도 비교한다.
5. 카메라 이동과 뷰포트 크기 변경을 반복한다. 크기가 32로 나누어떨어지지 않는 화면에서도 비교한다.
6. `Test_OffscreenPoint_*` 32개는 시작 카메라에서 벽과 큐브를 비추지 않는다. 존재 여부가 화면 조명에 영향을 주면 목록이나 인덱스 접근을 확인한다.

화면이 같다는 것만으로 광원이 실제로 줄었음을 증명하지는 못한다. 타일별 광원 개수를 확인하면 화면 밖 광원이 제거됐는지 판단할 수 있다. 현재 타일의 Near~Far AABB를 사용하는 방식은 필요 없는 광원을 일부 남길 수 있으므로 모든 타일의 개수가 반드시 최소가 될 필요는 없다.

현재 셰이더 생성이나 VS 바인딩 오류가 남아 있다면 먼저 해결한 뒤 비교한다. Compute만 끄고 타일 목록을 읽는 PS를 그대로 두는 방식은 기준 경로가 아니다.
